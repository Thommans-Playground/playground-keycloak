# /vbench:v-2-design: System · Architecture · Module

**Why this step:** deciding the structure and the tests up front keeps the code small and the tests honest.

Left arm, descending. Input: `$ARGUMENTS` (UC id, optional level; default = the levels the change touches).

**Precondition:** the UC spec has approved, testable ACs. If not, send the user to `/vbench:v-1-requirements`.

Read first: the project's methodology (`docs/00-engineering-methodology.md`), naming conventions, ADRs, any
security practices and context/domain diagrams that exist, and the closest sibling UC's spec, diagrams and
code. Design to match them.

## Constitution check
`docs/` is the project's constitution. Before the approval gate confirm the design contradicts no accepted
ADR, weakens no security practice, and breaks no naming convention. If it must contradict an ADR, do not edit
the old entry: draft a new ADR that supersedes it and put the conflict in front of the user.
In a project on the stack standard (`stack` in config), the accepted stack ADRs are the first thing to check, and the
layout, conventions and test mapping are in `references/stack-python-fastapi.md`.

## Set the rigor tier and say why
Default is the spec's `Rigor` field (`rigor_default` in config). The user may override.

Paths to `scripts/` and `references/` are relative to this skill's directory. Tiers are **light**, **standard** and **full**; what each produces, and when to escalate, is in
`references/rigor-tiers.md`. Read it before choosing.

## Pick the levels and say why
Most changes touch only **module**. Never design a level "for completeness".

| Level | Decide | Artifact | Verified by (commit to it now) |
|---|---|---|---|
| **system** | Which bounded context owns this? New cross-context interaction? | context placement in the spec; the **context map** if a context or cross-context edge is new | system-rung test |
| **arch** | Aggregates, entities, value objects; ports and adapters; the public interface; schema | class diagram; the context's **domain model** (tactical DDD) | integration-rung test + boundary check |
| **module** | Layering, flow, error translation, tasks | sequence diagram; delivery tasks | unit-rung tests |

## Frame the domain first (always)
**A. Bounded context.** Default to an existing context. Propose a new one only if the UC needs a model whose
terms conflict with an existing context's, or it has a different lifecycle or owner. State the neighbours and
the relationship to each (published language, anti-corruption layer, conformist). A new context or a new
cross-context edge is a system-level change: create or update the context map and draft an ADR.

**System-level files** (MK3's scheme; skeletons and conventions in `references/diagram-templates.md`):
- `NN-<context>-ddd.puml`: the context's domain model. First use case in a context: `vbench new context --name
  "<Context>"` allocates the tier (10, 20, ...) and writes the skeleton; later use cases extend it. Required at the
  full tier. On the python-fastapi stack the same command also creates the context's code package and rewrites the
  architecture contract, so the diagram, the package and the `boundaries` gate always agree.
- `09-context-ddd.puml`: the context map. Once a second context has a designed use case, `vbench new context-map`
  scaffolds it; you classify each context (Core, Supporting) and add one line per edge with its integration pattern.
  It is authored, never overwritten.
- `08-usecase-diagrams.puml`: generated by `vbench sync`; do not edit it.

**B. Ubiquitous language.** List every domain term the UC uses and check it against the requirements doc's
vocabulary, the context's domain model and the names already in code. Flag synonyms, homonyms, and terms in
the spec with no counterpart in code. Reuse an existing term; add a new one (append-only) with a one-line
definition; translate at the seam when a neighbour means something else. Ask the user only for terms the
docs and code cannot settle, with your recommended definition. Record the outcome under Design decisions. Fill the
table's *Not to be confused with* column: `vbench check vocabulary` fails a diagram that draws one of those words.

## Design method
Detail for each step is in `references/ddd-hexagonal.md` (aggregates, ports, boundaries) and
`references/patterns-and-forces.md` (which pattern answers which force).

1. **DDD first.** Name the aggregate and its invariants in the context's language. Identity → entity;
   defined by value → value object. Cross-context calls go only through the context's public interface.
2. **Hexagonal at the seams.** A port only where there is a real external dependency, a genuine second
   implementation, or a test that needs a fake. No port for in-process logic with one implementation.
3. **GoF only when a force demands it.** For each pattern, state the force in one sentence. If you cannot
   name the force, use plain code.
4. **Alternatives.** For a non-trivial interface, sketch two designs and pick one. Prefer deep modules: a
   small interface over substantial behaviour.
5. **Schema impact.** Name any new or changed column and how an existing database is migrated.
6. **ADR?** A decision that is expensive to reverse gets the next free `ADR-` id.

If a design choice is genuinely contested, interview the user with `../discovery/references/interview-technique.md`
(options, the forces, your recommendation) and record the outcome under Design decisions.

## Write into the spec
- **Implementation overview**: layer → file → responsibility, plus the seams named above.
- **Verification plan**: each AC → planned test file, rung, and the design level that justifies it. Every AC
  must appear; every level designed must name its rung test.
- **Diagrams**: the PlantUML files the tier requires (sequence at standard, plus class at full), named after the spec and
  linked in its **Diagrams** row. Give every sequence message a step id (`vbench id step --area <A>`, written `STP-<A>-<nnn>`
  in the message) so tasks, code and tests can cite it. Decide the spec's **Lifecycle** row: `yes` (something moves through states) requires the
  state diagram at any tier, `none` says there is none; the full tier needs the decision made. Skeletons,
  naming and colour conventions are in `references/diagram-templates.md`; `python3 scripts/render_diagrams.py`
  renders them if `plantuml` is installed (optional).
- **Delivery tasks**: fill the spec's task table, one row per commit-sized task, each ending in a passing
  test: `| **TSK-<area>-<nnn>** | description | the AC ids it closes | the step ids it builds |`. Cut tasks by walking the
  sequence diagram top to bottom: a task is one step or a few adjacent ones, a thin slice through the layers and
  never a horizontal layer such as "all the models". A task that turns on an open design decision is not safe to run
  unattended; settle the decision first. Every AC is closed by at least one
  task. Add no status column: a task is closed when its ACs have marked tests (`vbench status` shows it), so
  the table cannot drift from the code.
- **Design decisions**: D1…Dn with the force behind each choice.
- Run `vbench sync`, `vbench check diagrams` and `vbench check refs`.

## Gate
First hand the spec to the `spec-challenger` agent and fold what it finds into the design, or say why not. Summarise levels touched, aggregates/ports/patterns (each with its force), schema and ADR impact, the
verification plan and the tasks. Ask for approval; stop. Next: `/vbench:v-3-code <UC-id>`.
